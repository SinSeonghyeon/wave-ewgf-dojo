## 합류 순서와 의존성

- 선행 의존 브랜치: 없음. 이 브랜치는 `origin/main`의 누적 순위 구현을 기준으로 완결되어 있다.

- `main`이나 `feature/notices`에 이 브랜치에서 직접 병합하지 않는다. 통합 담당자가 `feature/notices`에서 합류한다.

## 사용자에게 보이는 변경과 공지

- 순위표의 본인 행에만 삭제 버튼이 보인다.

## 배포 전후 사용자 작업

D1 스키마 변경과 마이그레이션은 없다. 비밀값 추가·변경도 없다. Worker에 새 `DELETE /score` 경로가 생기므로 사이트보다 Worker를 먼저 배포해야 한다.

정확한 순서:

1. 통합 담당자가 이 브랜치를 `feature/notices`에 합류하고 충돌 해결·전체 테스트를 끝낸다.
2. 통합된 트리의 `worker/`에서 사용자가 `npx wrangler deploy`를 실행한다.
3. Worker 배포 성공을 확인한다. 기존 닉네임 토큰으로 본인 기록 삭제가 성공하고, 틀린 토큰과 허용되지 않은 Origin은 403이어야 한다.
4. 그 뒤에만 통합 결과를 `main`에 합류하고 사이트를 푸시한다.
5. 배포된 사이트에서 아래 수동 확인 항목을 수행한다.

구 사이트가 새 Worker와 함께 동작하는 것은 문제없지만, 새 사이트를 구 Worker보다 먼저 배포하면 삭제 요청이 실패하므로 순서를 바꾸지 않는다.

- `tests/dojo.test.cjs`: VM export 목록의 `boardDelete`/`renderBoard`, 백엔드 경합 테스트와 I18N 키 검증.
- `tests/smoke-chrome.js`: 닉네임 게이트의 예상 409 로그 정리, 순위 등록 뒤 삭제 UI→실제 Worker→가짜 D1 검증. 공지 스모크 흐름과 실행 순서를 함께 보존해야 한다.
- `AGENTS.md`: 설계 결정 20. 통합 브랜치의 새 설계 결정 번호와 충돌하면 내용을 보존하며 번호만 최종 정리한다.
- `.agents/docs/PLAN.md`, `.agents/docs/CODE_MAP.md`: 공지 브랜치 진행 로그와 백엔드 구조 설명이 겹칠 수 있다.
- `worker/index.js`, `worker/README.md`, `tests/board.test.cjs`: 다른 Worker 기능 브랜치가 있을 때 라우팅·CORS·API 표에서 충돌할 수 있다.

## 병합 시 반드시 보존할 동작

- 삭제 버튼은 `hasNick()`이 참이고 응답 `me.nick`의 `nickKey`가 현재 닉네임과 같은 본인 행에만 표시한다.
- 클라이언트가 행 ID를 보내지 않는다. Worker가 `{board,nick,token}`으로 소유권을 확인하고 시즌·보드·등록 철자가 일치하는 행만 삭제한다.
- `DELETE /score`도 허용 Origin 검사를 통과해야 하며, 잘못된 토큰은 403 `auth`이다.
- 삭제 성공 응답은 `/top`과 같은 `rows`, `me`, `total`, `cut10`을 포함해 UI와 웨이브 상위 띠를 즉시 갱신한다.
- 삭제해도 닉네임·토큰·로컬 연습 기록은 지우지 않는다.
- `/submit` 진행 중에는 삭제 실행과 버튼을 막는다. 삭제 중 시작된 등록은 삭제 완료 뒤 실행한다.
- 삭제 중 닉네임 변경으로 요청된 `boardLoad`는 `loadAfterDelete`에 예약하고, 삭제가 끝난 뒤 새 닉네임으로 실행한다. 오래된 `me`는 즉시 본인 표시에서 제외한다.
- 삭제 중에는 중복 삭제, 순위 탭 전환, 새로고침을 막고 완료 뒤 정상 복구한다.

## 테스트와 결과

- `node --test tests/dojo.test.cjs tests/board.test.cjs`: 통과, 97/97.
- `node tests/smoke-chrome.js`: 최종 통과, `errors: []`. 실제 Worker 핸들러와 가짜 D1을 통해 등록 → 본인 행 삭제 → DB 행 0개를 확인했다.
- `git diff --check`: 통과.

검증 중 해결된 실패:

- Chrome 152가 의도한 닉네임 점유 409를 두 번 기록해 스모크가 실패했다. 해당 점유 요청 직후 이미 수집된 예상 409만 모두 제거하도록 수정했다.
- `Runtime.evaluate` 전역에서 `const s`가 재선언되어 실패했다. 해당 평가문을 IIFE로 감쌌다.
- 느린 실행에서 삭제 직전의 불필요한 `boardRefresh`가 고정 800ms 안에 끝나지 않아 삭제 버튼이 `null`인 실패가 있었다. 중복 새로고침을 제거하고 기존 본인 행의 버튼 출현을 조건 대기하도록 수정했다.
- 테스트 전용 `dojo-smoke-profile` Chrome 자식 프로세스가 남아 CDP 응답이 지연된 경우가 있었으며, 해당 테스트 프로필 프로세스만 정리한 뒤 최종 검증했다.

## 합류 후 브라우저 수동 확인

1. 닉네임이 있는 상태로 측정 모드 하나를 완주해 순위표 본인 행과 삭제 버튼이 보이는지 확인한다.
2. 다른 사람 행에는 삭제 버튼이 없고, 본인 행의 삭제를 취소하면 아무 변화가 없는지 확인한다.
3. 삭제를 확인하면 성공 문구, `등록한 기록이 없습니다`, 빈 표 또는 남은 다른 사람 행이 즉시 맞게 표시되는지 확인한다.
4. 닉네임과 로컬 최고 기록이 유지되는지 확인하고, 같은 측정을 다시 완주하면 새 서버 기록이 등록되는지 확인한다.
5. DevTools에서 느린 네트워크를 적용해 등록 중 삭제 버튼이 비활성화되는지 확인한다.
6. 느린 삭제 중 닉네임을 변경했을 때 이전 닉네임 행이 본인 강조·삭제 버튼을 잃고, 삭제 완료 후 새 닉네임 기준 순위가 로드되는지 확인한다.
7. ko/en/ja에서 삭제 버튼·확인·진행·성공·실패 문구와 통합 공지가 모두 번역되는지 확인한다.
