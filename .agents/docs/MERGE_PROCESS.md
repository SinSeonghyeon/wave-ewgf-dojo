# 다중 브랜치 합류 절차

여러 기능 브랜치를 통합 브랜치에서 모아 한 번에 `main`으로 보낼 때 쓰는 절차다. 프로젝트 전용 규칙이므로 개인 환경의 Codex 스킬로 만들지 않고 저장소에서 공유한다.

## 기능 브랜치가 남길 것

기능 브랜치마다 `.agents/handoffs/<브랜치명>.md` 파일을 하나 커밋한다. 브랜치명의 `/`는 `-`로 바꾼다. 예: `feature/notices` → `.agents/handoffs/feature-notices.md`.

아래 항목을 짧더라도 모두 작성한다.

1. 브랜치명, 인수인계 기준 커밋, 한 줄 목적
2. 합류 순서와 의존 브랜치
3. 사용자에게 보이는 변경과 공지 필요 여부
4. 공지가 필요하면 ko/en/ja 제목·요약·항목 초안
5. 배포 전후에 사람이 해야 할 작업(Worker 재배포, D1 마이그레이션, 비밀값, 도메인 등)과 정확한 순서
6. 충돌 가능성이 큰 파일·심볼과 병합 시 반드시 보존할 동작
7. 실행한 테스트, 결과, 알려진 실패·미완료
8. 바뀐 설계 결정과 갱신한 문서
9. 합류 후 브라우저에서 직접 확인할 항목

비밀값·토큰·개인정보는 인수인계 문서에 쓰지 않는다. 필요한 경우 비밀값의 이름과 사용 절차만 적는다.

## 공지 초안 형식

공지 필요 여부가 `예`이면 다음 표를 채운다. 통합 담당자가 여러 브랜치의 초안을 한 공지로 합치거나 별도 공지로 나눌 수 있다.

| 언어 | 제목 | 요약 | 항목 |
|---|---|---|---|
| ko |  |  | 1. …<br>2. … |
| en |  |  | 1. …<br>2. … |
| ja |  |  | 1. …<br>2. … |

공지에 들어갈 최종 문자열은 설계 결정 7·20에 따라 `index.html`의 ko/en/ja I18N 사전에 같은 키로 추가한다. `NOTICES`는 최신순이며, 같은 배포 묶음의 여러 기능을 한 공지에 합칠지는 통합 담당자가 사용자에게 확인한다.

## 통합 담당자 체크리스트

1. 전용 통합 브랜치를 만들고 `main`은 건드리지 않는다.
2. `.agents/handoffs/*.md`를 모두 읽고 의존 순서·선행 배포 작업을 표로 정리한다.
3. 충돌을 해결할 때 각 인수인계의 "반드시 보존할 동작"을 대조한다.
4. 공지 초안을 ko/en/ja로 합치고 `NOTICES` 최신 항목과 I18N 키를 갱신한다.
5. `PLAN.md`, `CODE_MAP.md`, 필요 시 `README.md`와 `AGENTS.md`의 최종 상태를 한 번만 정리한다.
6. 선행 Worker 배포·D1 마이그레이션이 필요한 기능은 사이트 푸시 전 사용자 작업 여부를 확인한다.
7. 단위 테스트 → Chrome 스모크 테스트 → 브라우저 수동 확인 순서로 검증한다.
8. `git status --short`와 `git diff main...HEAD --stat`로 합류 범위를 확인한다.
9. 모든 인수인계가 코드·공지·문서에 반영됐으면 `git rm .agents/handoffs/*.md`로 임시 문서를 삭제한다.
10. `git ls-files .agents/handoffs` 결과가 비었는지 확인한 뒤에만 `main` 합류 준비 완료로 보고한다.

인수인계 문서는 기능 브랜치와 통합 과정에서만 존재한다. `main`에는 `.agents/docs/MERGE_PROCESS.md`와 이 규칙만 남고 `.agents/handoffs/` 파일은 남기지 않는다.
