# D1 사용량 전체 검토 (2026-09-21 KST)

아래 최초 검토의 실측·제안은 당시 기록이며, 이후 로컬 구현과 재리뷰 결과는 문서 끝에 덧붙였다.

범위: Worker SQL·실서버 인덱스/실행 계획·프런트 요청 경로·최근 1일/7일 Insights. 검토만 수행했으며 앱/Worker 코드·스키마·배포는 변경하지 않았다. 원격 실험은 SELECT/EXPLAIN만 실행했다.

## 실측

최근 1일 Insights 반환 쿼리 합계는 1,217,032 읽기 행이다. UTC 기준 당일 계정 전체 사용량과는 기간·범위가 다르며, 메일에 적힌 9월 17일 한도 도달 여부를 이 수치로 판정할 수 없다. 다른 D1 DB 사용량과 트래픽 출처는 이번 조사에 포함되지 않는다.

| 경로 | 읽기 행 | 실행 수 |
| --- | ---: | ---: |
| 순위 계산(조회·등록·삭제 공용) | 1,180,370 | 364 |
| 한마디+투표 집계 | 21,160 | 154 |

순위 계산이 약 97.0%. 순위 쿼리 평균은 3,242 읽기 행이다. 최근 7일에도 현재 순위 쿼리가 15,522,351행/5,866회로 가장 크며, 종전 분리 쿼리도 기간 내 존재한다. 과거 쿼리가 포함된 7일 통계를 현재 배포 비용으로 해석하면 안 된다.

현재 scores: wave10 252, ewgf20 191, bd10 150, rush30 113, combo10 79, wsc 4. nicks 1,575개, bans 5개. scores_rank·scores_nick·replies_post_id·votes PK 모두 원격에 존재한다. PLAN의 과거 보드당 600~850행 추정은 현재 실측과 다르다.

## 우선순위 1: 차단 조회의 전체 닉네임 스캔 제거

위치: worker/index.js의 BANNED(96행), top(131행).

현재 `FROM nicks n JOIN bans b ON b.key=n.key`의 원격 실행 계획은 `SCAN n` → bans key 검색이다. 차단된 닉 5개를 찾으려고 등록 닉네임 1,575개를 전부 훑는다. 가입만 하고 순위에 참여하지 않는 방문자도 이후 모든 순위 조회 비용을 키운다.

후보: `FROM bans b CROSS JOIN nicks n ON n.key=b.key`. SQLite의 CROSS JOIN 순서 고정을 사용해 작은 차단 목록을 먼저 읽고 nicks PK로 찾는다. UNION의 기존 닉 표기·등록 후 표기 병합 의미는 유지한다. 단순히 JOIN 좌우만 바꾸면 옵티마이저가 다시 순서를 바꿀 수 있다.

원격 wave10 익명 조회의 **전체 순위 SQL**을 전후 각 1회 실행한 결과:

| | 읽기 행 | 쓰기 행 |
| --- | ---: | ---: |
| 현재 | 3,870 | 0 |
| 후보 | 2,300 | 0 |

반환 행·순위·total·cut 위치가 JSON 비교로 동일했다. 1,570행, **40.6% 감소**. 현재 데이터의 단일 보드/익명 비교이며 전체 트래픽 절감률을 보장하지 않는다. 닉 지정·차단 당사자·등록 전 차단/등록 후 표기 변경은 구현 시 기존 회귀 테스트와 함께 검증해야 한다. 스키마 변경 없이 Worker 수정·재배포만 필요하다.

## 우선순위 2: 중복 요청 억제

index.html의 boardLoad는 seq로 낡은 응답을 버리지만 이미 발송한 요청의 DB 비용은 남는다. boardRefresh는 삭제 중에만 비활성화된다. 한마디에는 이미 postsLoading 가드가 있다.

- 같은 보드·같은 닉의 진행 중 요청을 공유하고 새로고침 중 중복 요청을 막는다. 탭 전환/닉 변경/점수 등록·삭제의 rev/seq 보호는 유지한다.
- 선택 사항: 탭 왕복 시 짧은 로컬 캐시를 사용한다. 수동 새로고침과 등록·삭제 뒤에는 최신 데이터를 조회한다. 최신성 정책 변경이므로 캐시 시간은 구현 전에 정한다.
- 서버 GET /top·/posts·/visits와 POST /submit·/visits에는 현재 횟수 제한이 없다. 비정상 반복 호출이 확인되면 D1 진입 전 제한을 추가한다. 실제 게임의 정상 제출 속도·공유 IP를 고려해야 하며, 이번 Insights만으로 봇이 원인이라고 단정하지 않는다.
- CORS는 GET의 DB 실행을 막지 않는다. 허용되지 않은 Origin을 먼저 거르는 것은 보조책일 뿐, Origin을 위조할 수 있는 비브라우저 호출에 대한 방어는 아니다.

## 우선순위 3: 순위 공통 결과를 저장해 재사용

차단 스캔을 없애도 세 window 함수(RANK/ROW_NUMBER/COUNT)가 보드 전체를 처리한다. 상위 10개만 반환한다고 10행만 읽는 것은 아니다. `/submit`은 최고 기록 갱신이 없어도 매번 top을 실행한다.

반복 경고가 지속되면 D1에 보드별 공통 집계(상위 10·참가 수·cut10)를 저장하고 **실제 최고 기록 변경/삭제/차단 변경 때만** 갱신하는 구조를 권장한다. 현재 1일 순위 계산 364회 대 점수 제출 66회이므로 재사용 여지가 있지만, 개인 순위 계산·집계 갱신 자체 비용·추가 쓰기를 포함해 벤치마크해야 한다. 감소율은 아직 미측정이다.

개인 me·차단 당사자의 total/rows/cut10은 공통 결과와 분리한다. `nick`을 무시해 전체 응답을 공유 캐시하면 남의 me와 잘못된 차단 상태가 섞인다. 닉 등록(차단 후 다른 표기로 등록 포함), 관리자 점수 삭제, ban/unban 등 모든 변경 경로와 동시 요청의 원자성을 설계해야 한다. 기존 결정 24 변경 및 사용자 스키마 적용·Worker 배포가 필요하다.

대안은 Worker Cache API의 짧은 캐시다. 다만 캐시·삭제가 데이터센터별이므로 모든 지역에서 즉시 무효화를 보장하지 않는다. 현재 낮은 요청 밀도에서 짧은 TTL의 적중률은 미측정이며 '90% 절감' 같은 수치를 약속할 근거는 없다.

## 나머지 경로

- 한마디·순위 자동 폴링은 이미 없다. 1분 타이머는 열린 탭의 KST 날짜 변경 방문 집계만 처리한다. BGM·WebGL·키보드 입력은 D1 읽기와 관계없다.
- 한마디는 최신 50글을 먼저 제한하며 투표/답글 인덱스가 있다. 글·투표·답글 변경 때 전체 50글과 답글을 다시 반환하지만 현재 비용은 약 2.9%라 순위보다 후순위다. 글 수를 5개로 줄이거나 답글을 숨기는 UX 변경은 권장하지 않는다.
- 방문자의 SUM은 모든 날짜를 읽지만 현재 8행/회·약 0.08%다. 장기적으로 누적 합계 1행을 유지할 수 있으나 지금 우선할 이유는 없다.
- 인증은 key 인덱스로 1행 조회한다. 토큰을 공유 캐시에 넣지 않는다.
- 현재 인덱스가 누락된 상황은 아니다. 인덱스를 무작정 추가하면 쓰기 비용이 늘며, 전체 window 집계의 근본 비용은 남는다.

## 권장 실행 순서와 검증

1. 차단 조회 수정 + 순위 중복 요청 억제. 동작 규칙을 유지하는 작은 변경부터 진행.
2. 단위 테스트 → Chrome 스모크. 동점 순위·내 행·차단/해제·최고 기록 유지/개선·삭제·6개 보드 확인.
3. 사용자가 Worker 배포, 프런트 변경이 있으면 사이트 푸시. 배포 직후 동일 SELECT 비용 비교, 다음 24시간/혼잡일 Insights 확인. UTC 당일 계정 전체 사용량은 대시보드에서 별도로 확인.
4. 그래도 여유가 부족하면 보드 공통 집계 설계. 유료 전환은 잔여 사용량·트래픽을 보고 결정.

이번 작업은 검토 문서만 변경하므로 단위/브라우저 테스트는 실행하지 않았다. 실서버 SELECT 전후 결과 동일·rows_written=0 확인. 임시 SQL·응답은 gitignore된 `.sandbox/d1-review/`에 보관했다. `--file` 실행은 합계 메타만 제공해 최종 비교에 쓰지 않았고, 이후 `--command`로 개별 비교했다. 중간 셸 인자 전달 실패는 수정 후 재실행했다.

## 로컬 구현 재리뷰 (2026-09-21)

검토 범위는 미커밋 D1 차단 조회 최적화, 순위 진행 중 요청 공유, 관련 테스트·문서다. 우선순위 1·2는 로컬 구현됐으며 완료 결과 캐시·집계 테이블은 추가하지 않았다.

- **P2 수정 — 인증 만료 후 순위 로딩 상태 잔류:** `/top` 진행 중 투표 등의 403이 `lostNick()`을 호출하면 요청 키가 달라진다. 기존 로컬 변경은 늦은 응답을 버리면서 `board.loading`을 정리하지 않아 문구가 계속 남고, 응답 도착 전에는 새로고침도 비활성 상태였다. `lostNick()`에서 seq 무효화·로딩 문구 해제·화면 갱신을 처리했다. 투표 403 → 익명 재조회 → 이전 닉 응답 → 새 응답 순서의 회귀 테스트를 추가했고 수정 전 실패를 확인했다.
- **유지보수성 수정:** 요청 Promise를 지역 변수로 보관하고, 키에 이미 포함된 rev의 중복 스냅샷/비교를 제거했다. 공유 요청에 매달린 이전 호출들은 화면을 다시 그리지 않으며 마지막 호출만 결과를 반영한다.
- Worker SQL에서는 추가 동작 오류를 발견하지 않았다. 인덱스 검색 실행 계획 검사와 기존 섀도 밴·표기 변경·본인 순위·삭제 테스트를 통과했다. 이번 재리뷰에서 원격 DB 조회나 배포는 수행하지 않았으므로 위 실측 수치는 새로 측정한 결과가 아니다.
- 최종 검증: 단위 158/158·`git diff --check` 통과. Chrome 전체 스모크 첫 실행은 WSC 순위 등록 대기 시간 초과(exit 1). 실패 시 도전 상태·과제·순위 문구·열린 대화상자·로컬 DB의 WSC 행을 출력하도록 진단만 보강한 재실행은 통과(exit 0, errors=[]; WSC 10/10·최고 10연속·1위 등록/삭제 포함). 최초 실패의 원인은 미확정으로 남기며, 진단 추가를 문제 해결로 간주하지 않는다.
